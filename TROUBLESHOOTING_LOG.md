# Project Deployment & Troubleshooting Log

This document outlines the key challenges faced and solutions implemented during the deployment of the Tracki project.

---

## 1. Initial Project Configuration

### Problem: Hardcoded URLs and Missing Environment Examples

- The frontend code contained hardcoded API endpoints, making it difficult to switch between local development and a production environment.
- The backend lacked an example environment file (`.env.example`), making it unclear which variables were required to run the application.

### Solution: Centralized Configuration

- **Frontend**: A utility function `getApiUrl` was created in `frontend/lib/api.ts`. This function reads the backend URL from the `NEXT_PUBLIC_API_URL` environment variable. A `frontend/.env.example` file was created to document this.
- **Backend**: A `backend/.env.example` file was created to document the necessary `DATABASE_URL`, `JWT_SECRET_KEY`, and `CORS_ORIGINS` variables.

---

## 2. Backend Deployment to Azure

This was the most challenging phase, with several layers to the final problem.

### Problem 1: Incorrect Database Driver

- The initial choice, PostgreSQL, was not available on the user's Azure plan.
- **Solution**: We switched to **Azure SQL Database**. This required changing the Python database driver in `backend/requirements.txt` from `psycopg2-binary` to `pyodbc`.

### Problem 2: Incorrect GitHub Actions Workflow

- The default deployment file generated by Azure for the App Service did not account for our monorepo structure. It was trying to run the Python application from the root directory instead of the `/backend` directory.
- **Solution**: The auto-generated `.github/workflows/main_tracki-api.yml` file was heavily modified. The complex `build` and `zip` steps were removed, and a `package` parameter was added to the deploy step: `package: './backend'`. This explicitly told Azure where to find the application code.

### Problem 3: The "Login timeout expired" Error

This was the most persistent error and had several causes we had to eliminate. The error means the application server could not establish a connection with the database server.

- **Initial Diagnosis (Incorrect)**: A firewall issue. We attempted to manually add the App Service's outbound IP addresses to the SQL Server's firewall rules. While a good step, it wasn't the root cause.

- **Root Cause**: The environment variables, specifically the `DATABASE_URL`, were not correctly set within the Azure App Service's own configuration panel. The deployed code had no "knowledge" of the database's location or credentials.

- **The Final, Successful Solution**:
    1.  We deleted the old resources that were created separately.
    2.  We created a new **"Web App + Database"** resource directly within Azure. This is the **recommended approach** as it automatically configures the networking and firewall rules to allow the two services to communicate.
    3.  Azure automatically created several `AZURE_SQL_...` variables (server, user, password, etc.) in the App Service's **Configuration > Application settings** page.
    4.  Using these pieces, we manually constructed the full `DATABASE_URL` connection string required by our Python code and added it as a new application setting.
    5.  We also added the `JWT_SECRET_KEY` and `CORS_ORIGINS` variables here.
    6.  After **Saving** these new settings, the application was able to connect to the database successfully.

## 3. Frontend Deployment to Cloudflare Pages

### Problem: Production Build Fails Due to Linting Errors

- The frontend code contained several "unused variable" warnings. While these are ignored during local development (`npm run dev`), the production build command (`npm run build`) used by Cloudflare treats these warnings as critical errors, causing the build to fail.

### Solution: Ignore Linting Warnings During Build

- To get the application deployed quickly, we configured Next.js to ignore these warnings during the build process.
- The `frontend/next.config.mjs` file was modified to include the `eslint` configuration block:
  ```javascript
  /** @type {import('next').NextConfig} */
  const nextConfig = {
    output: 'standalone',
    eslint: {
      ignoreDuringBuilds: true,
    },
  };

  export default nextConfig;
  ```
- After committing and pushing this change, the Cloudflare build succeeded.

## 4. Final Security Step

### Task: Update CORS Policy

- After the frontend was successfully deployed and a URL was generated (e.g., `tracki.pages.dev`), the final step was to enhance security.
- **Action**: We must update the `CORS_ORIGINS` environment variable in the Azure App Service configuration. Its value should be changed from the permissive `*` to the specific URL of the deployed frontend. This ensures that only our web application can send requests to our API.
